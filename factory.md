# Factory

A personal software factory on an isolated Mac mini. Autonomous coding agents (Claude Code) pick up tasks and work on my own GitHub repos. Useful first. Follows the Keycard Software Factory reference architecture and Agent Baseline controls where that is reasonable for one user on one machine.

Reviewed against a second opinion on 2026-10-28. Changes from that review are marked `(review)`.

## Non-goals for v1

Egress proxy / enforced network allowlist, Temporal, Socket, OpenShell, Kubernetes, Linear intake, agent registry tooling, multi-tenant, more than one concurrent job.

## Trust boundary (review)

The **orchestrator** on the mini is the trust boundary, not the container. It reads the task, mints credentials, builds the `docker run` command from a fixed schema, and collects results. Nothing the agent writes or says can change image, mounts, flags, repo, or token scope. Task text, repo contents, and tool output are untrusted input.

Commits are attributed to the GitHub App's bot user (`kmaida-software-factory[bot]`, email `<id>+kmaida-software-factory[bot]@users.noreply.github.com`). The orchestrator resolves the id from the public users API at the start of every run, records it in the manifest as `git_identity`, and passes it to each container as `GIT_AUTHOR_*` and `GIT_COMMITTER_*`, so the image holds no identity and the safety-net commit uses the same one. A ruleset that requires approval of unattributed changes then accepts a single human approval; the earlier made-up `factory[bot]` identity could not be attributed to any account, and keycard-workshop-platform#9 stayed `REVIEW_REQUIRED` after approval. If the lookup fails the run does not start.

## Components

### 1. Sandboxed execution

- One fresh Linux container per job (Docker Desktop or OrbStack). On macOS that is a Linux VM, so the boundary is the VM plus the container, which is stronger than Docker on a Linux host.
- Only the cloned repo is mounted, as the writable workdir. Read-only root FS. Non-root user. No Docker socket, no host home, no host network.
- Image pinned by digest. Limits: `--memory 4g --cpus 2 --pids-limit 512`, wall-clock timeout 60 min, orphan cleanup on orchestrator start. (review)
- Container is removed after the job. Artifacts are the pushed branch, the run manifest, and the run log.

### 2. No static secrets in the sandbox

- Each container gets exactly one secret, delivered over stdin as a 0400 file on a tmpfs mount, never as a `docker run` argument: the worker gets the Claude credential, the judge gets the Codex key, the push step gets the GitHub token. The worker and the judge never hold a GitHub token. (review)
  - `github_token`: a GitHub App installation token scoped to the one target repo with `contents:write` only, so the push step can push and nothing else: it cannot open, approve or merge a pull request. The orchestrator mints it for the clone and again for the push: it fetches the App's private key from Keycard Vault (resource `urn:factory:github-app-key`, a dependency of the orchestrator Application, policy-checked and audited like the Anthropic resource), signs a 10-minute app JWT in memory, looks up which installation of the App covers the repo (`GET /repos/<owner>/<name>/installation`), and calls `POST /app/installations/<id>/access_tokens` with the repo and that one permission. After the container exits, the host mints a second token with `pull_requests:write` and `contents:read` and makes the one API call that opens the PR; the container never holds it. `contents:read` is needed because `POST /repos/<owner>/<name>/pulls` resolves the head and base refs, which on a private repo returns 422 `not all refs are readable` without it; the PR token can read refs but still cannot push, approve or merge. The key is not stored on the mini. Keycard has no GitHub App connector, so repo scoping happens in the orchestrator's minting call, not in Keycard.
  - `openai_key`: the Codex judge's API key, a Keycard Vault API Token credential on the resource `https://api.openai.com`, fetched per judge round, policy-checked and audited like the App key. Keycard returns the stored key verbatim with no `expires_in` (svc-sts `SecretProvider` sets no lifetime on vault credentials), so its lifetime is the OpenAI key's own: it lasts until revoked at OpenAI or replaced in the Vault. Fetching per round gives an audit trail, not an expiry.
  - `anthropic_token`: the Claude Code credential, issued per worker round with no API key anywhere. The orchestrator authenticates to the software factory zone as its own Application (`urn:factory:mini`) and gets a one-hour Keycard-signed OIDC token for the `https://api.anthropic.com` resource, policy-checked and audited. It exchanges that at Anthropic's Workload Identity Federation endpoint for a one-hour bearer token bound to the `factory` workspace and the `factory-mini` service account. The container uses it as `ANTHROPIC_AUTH_TOKEN`.
- No PAT, no `gh auth` cache, no `.claude` auth in the image. The Anthropic and GitHub tokens live one hour, the per-container timeout.
- Known limit: a token copied out during the run stays valid until it expires or is revoked. The run log redacts both tokens (literal and the Basic-auth base64 form); that is a mitigation against accidental leaks in output, not a guarantee, since an encoded or split token survives it.
- GitHub cannot scope an installation token to a branch, so the agent's token can also push to any other branch of the target repo that no rule protects, and to other open PR branches. The ruleset protects `main`, and "dismiss stale approvals" means a push onto someone else's approved PR removes the approval rather than riding it.

### 3. Intake and task binding

- One intake for v1: a task file in `queue/` on the mini, written by me, readable but not writable by the container. (review)
- Job schema: `{repo, base_branch, task_id, instructions}`. The orchestrator validates it and derives everything else. The agent never sees or edits the job file.
- Keycard zone policy grants the run authority for that repo only.

### 4. Run manifest and log (review)

- `runs/<run_id>/manifest.json`: job hash, repo, base commit SHA, image digest, model and Claude Code version, Keycard grant id, start/end time, final commit SHA, PR URL (or `pr_error` with the HTTP status and body when opening it failed), exit status.
- `runs/<run_id>/log.jsonl`: one line per tool call and per token issue, with run id, timestamp, tool, redacted arguments, exit status. Written by the orchestrator from the agent's stream, so the agent cannot rewrite it.
- Keycard zone audit covers the authorization side.

### 5. Judge before the human gate

- No human sees the code before an independent model has tried to refute it. After each worker round the orchestrator runs Codex in its own container against a fresh clone of the worker's checkout (read-only mount of the worker's tree, agent config files stripped, instructions from `judge-prompt.md` in the factory checkout, never from the target repo). The judge reads the diff, runs the repo's checks, hunts for wrong or out-of-scope changes and weakened tests, and ends with `VERDICT: VERIFIED | CAVEATS | REFUTED` plus findings.
- Anything but VERIFIED sends the findings back to the worker as a revision round on the same branch, up to `MAX_ROUNDS` (3). A revision round that produces no new commit ends the loop.
- The branch is pushed after the loop whatever the verdict (evidence). The PR opens only on VERIFIED or CAVEATS, with the verdict and findings in the body. REFUTED exits 5 and a missing verdict exits 6, both without a PR. Each round's full review is kept as `runs/<run_id>/judge-<round>.md`.
- The judge is a model and can be wrong both ways; it narrows what reaches the human, it does not replace them.

### 6. Human gate on merge

- The host opens the PR after a passing verdict. CI runs. I merge.
- Enforced in GitHub, not by instruction: a ruleset on `main` (PR required, one approval, stale approvals dismissed, required check), the agent's token cannot review or merge, and the App is not in the bypass list. (review)
- Target-repo requirement: workflows that run on `pull_request` must not use repository secrets. A `factory/*` branch is a same-repo branch, so GitHub gives its workflow runs the repo's secrets, and the agent can change any script those workflows execute. The App has no `workflows` permission, so it cannot edit the workflow files themselves. `plan-my-today`'s CI uses dummy values and no secrets.

### 7. Kill switch

- One script, `factory stop <run_id>`: stops the run's container, blocks new dispatch, and records the incident (in the log always; in the manifest when no live orchestrator will finalize it). Revocation is not wired: the orchestrator keeps no token to revoke, and both expire within the hour. (review)
- Known limit: revocation does not undo work already pushed. The PR gate catches that.

## Flow

```
task file in queue/
  -> orchestrator validates job, creates run_id, writes manifest
  -> orchestrator mints repo-scoped GitHub token from the App, fetches Claude credential from Keycard
  -> each container gets its one secret over stdin, landing as a 0400 file on tmpfs
  -> docker run (pinned image, repo mount, secrets mount, limits)
  -> worker container: agent works and commits; orchestrator streams tool calls to log.jsonl
  -> judge container: Codex reviews a fresh clone, writes findings + VERDICT
  -> not VERIFIED and rounds left: worker container again with the findings; else continue
  -> push container pushes the branch; host opens the PR only on VERIFIED or CAVEATS
  -> containers removed, manifest finalized (judge rounds and verdict recorded)
  -> human reviews and merges
```

## Accepted risks for v1

- Open egress from the containers. The worker can exfiltrate the repo and its Anthropic token over HTTPS. In the judge container, the repo's own checks run as the same user as Codex with no inner sandbox, so a test the worker wrote can read Codex's login under `/tmp/codex` and send the judge's key out (v1's CI judge had the same exposure). The git helper only answers for github.com, so a push to another host carries no credential, but `curl` would. Mitigations in place: the judge's key is judge-only and rotatable, the verdict is collected from a mount the repo cannot reach, and anything the judge writes is redacted for its key before it is reused. Revisit with the Keycard egress proxy, or a credential-free check container feeding the judge, when this matters.
- Single machine, single user, no evidence integrity.

## Files

- `factory.md`: this spec.
- `Dockerfile`: the sandbox image; one entrypoint with three modes (`work`, `judge`, `push`), one container per step.
- `worker-prompt.md`: the house rules prepended to every worker round (least code that satisfies "Done when"; no speculative abstraction; one test per behaviour; no new dependencies), read from this checkout.
- `judge-prompt.md`: the judge's instructions, read from this checkout, never from the target repo. Over-engineering is a finding with the weight of a bug and earns CAVEATS, so bloat costs the worker a revision round. Every round reports every finding the judge can establish, ranked, each marked `NEW:` or `REPEAT:` against the previous round's findings, which the orchestrator appends to the judge's prompt from round 2 on (run `011-wp-join-core`, 2026-10-31, was refuted in round 3 by a finding first raised in round 3, with no round left to fix it).
- `tasks.md`: task-writing conventions for unattended runs; `factory lint` checks a queue against them and `batch` refuses to start on problems.
- `factory`: orchestrator script (`run`, `lint`, `batch`, `report`, `stop`). `batch` is the overnight loop (section below). `run` exits with the worker's status, or 3 when the agent produced no commits (nothing pushed), 4 when the branch was pushed but opening the PR failed, 5 when the judge refuted the final round (pushed, no PR), 6 when the judge gave no verdict (pushed, no PR).
- `test-factory.sh`: runs the orchestrator against stubbed `docker` and `curl` and checks the revise / refuted / no-verdict / caveats paths, CRLF, doubled and oversize verdict files, the judged-round count, log redaction, lint and batch (chain, refuted chain, `--max-tasks`, `--stop-at`, HALT between tasks, `--no-chain`, `--continue`, a declared dependency on a failed task, a run killed before its cleanup, task files byte-identical after the move), the GitHub App path (installation lookup, 404, refused mint, PR open, PR reconciliation, chained PRs targeting `base_branch`) and `stop` with docker down. Every fix for a misreported outcome lands with a case here that fails against the previous script.
- `queue/`, `runs/`: task intake and per-run evidence. Not in the image.

## Batch and overnight runs

`factory batch [queue-dir] [--max-tasks N] [--stop-at HH:MM] [--no-chain] [--continue]` runs a queue (default `queue/`) unattended without waiting for anything to merge. A run on its own bases on `base_branch` and stops; a second task that builds on the first has nothing to build on until a human merges, so an overnight queue would stall after one task. `batch` chains instead.

- **Chaining.** Tasks run in filename order under one lock (each run borrows it and hands it back). The first task bases on its own `base_branch`. Every task after a task that exited 0 cuts its branch from `factory/<previous task_id>`: `batch` passes it to `run` as `FACTORY_CHAIN_BASE`; the task file is never changed. The PR still targets the task's own `base_branch` (a PR opened against `factory/<prev>` fails with 422 "base ref not found" once that branch is merged and auto-deleted mid-batch), so a stacked PR shows the earlier task's commits until it merges. The manifest records `base_branch` (the PR base) and `chain_base` (the branch it was cut from, null when not chained). `--no-chain` makes every task base on its own `base_branch`.
- **Stopping.** Any exit other than 0 (3 no changes, 4 pushed but PR failed, 5 REFUTED, 6 no verdict, a timeout, a token failure, a stop) ends the batch: that task's file moves to `<queue-dir>/failed/`, every later task stays in the queue untouched. `--continue` goes on instead: the failed task goes to `failed/`, every later task whose base (its own `base_branch`, or the chain) names a task that failed tonight is moved to `failed/` unrun, since that branch was pushed as evidence and must not be built on, and the chain resumes from the next task's own `base_branch`. `--max-tasks N` and `--stop-at HH:MM` (today at that local time: no task starts once it has passed, so a time already past means nothing runs; a batch meant to cross midnight should start after it) stop the batch between tasks in the same way, moving nothing further. A chained queue targets one repo; `batch` refuses a mixed one unless `--no-chain`.
- **Task files.** Exit 0 moves the file to `<queue-dir>/done/<run_id>.json`, anything else to `<queue-dir>/failed/<run_id>.json` (`run_id` is `<timestamp>-<task_id>`, and lint makes `task_id` the filename; a task that died before it became a run gets `batch-<timestamp>-<name>.json`). A rerun of `batch` therefore never repeats a task. The bytes do not change, only the path. This is what happens to a task file after its run; a bare `factory run` still leaves the file where it is.
- **Report.** `runs/batch-<timestamp>.md`: one row per task with the `report` columns (run, exit, judge rounds, verdict, PR) plus the chain base and the duration, and the reason the batch stopped if it did. The path is printed last. `batch` exits with the status of the run that stopped it, 0 otherwise.
- **Notify.** With `FACTORY_NOTIFY_URL` set (an env var like `FACTORY_SECRETS_DIR`, never a constant in `factory`), every task that exits non-zero POSTs one line to it with curl: `<batch_id>: <task name> exited <rc> (<verdict or ->, <continuing|stopped>)`. Silent, 10 s timeout, a failed POST is ignored; the URL goes to curl as config on stdin, not argv, since webhook URLs often carry a token. `batch` refuses to start on a URL with quotes, backslashes or whitespace, which could break that config. Nothing is sent for a passing task or a task skipped unrun (GitHub already notifies on every PR the App opens). When the loop is over, one summary line follows whatever happened: `<batch_id>: done: <n> run, <k> PR(s), <f> failed. <All tasks ran.|Stopped: <why>. <m> task(s) left in queue.>`, so a night with no message at all means the batch never reached its end (refused at start by lint, `HALT` or the lock, or killed). The body is raw text, so an ntfy topic (`https://ntfy.sh/<topic>`, the topic being the secret) works as is; a Slack webhook would need a JSON body.
- **Stop.** `factory stop <run_id>` writes `HALT` and signals the run; the run exits non-zero and goes to `failed/`, and the batch loop sees `HALT` before the next task and exits, moving nothing else. `batch` also refuses to start while `HALT` exists.
- **Why `main` is never merged by the mini.** Chaining needs no merge: each branch is pushed by the push container with a `contents:write` token and the PR is opened by the host with `pull_requests:write`. Nothing on the mini holds approval or merge rights, the App is not in the ruleset's bypass list, and the trust boundary, container flags, secrets delivery and judge are exactly those of a single `run`.
- **Morning routine.** `factory report`, then the stack bottom-up: every PR targets its task's `base_branch` (normally `main`), so a later PR's diff includes the tasks below it until they merge. Review and merge the bottom PR; the next one's diff shrinks to its own commits. A task in `failed/` has its reason in `runs/<run_id>/manifest.json` and `judge-<round>.md`; to re-queue it, copy the file back into the queue under a new `task_id` (the old `factory/<task_id>` branch exists, so a rerun with the same id is refused), append the judge's findings to its instructions, and run `batch` again. Everything that was queued after it is still there and will chain on the re-queued task.
- **Blocked tasks.** Task instructions should tell the worker that when it cannot complete the task, it commits `docs/BLOCKED-<task_id>.md` with the reason instead of stopping. The run then has a commit, the judge refutes it with the reason in front of it, and the chain stops with evidence in `judge-1.md` and the pushed branch, instead of a silent exit 3.

Factory-side events (clone, secrets issued, exit) use `type:"factory"`.

- **Outcome handling rules (after three misreported runs, 2026-10-31):** the orchestrator's job is to say what happened; a wrong manifest costs a morning. So: (1) parse the complete response before bounding any copy of it, and bound only what goes to the log and manifest; (2) check the HTTP status and curl's result before the body, and keep the status and a bounded body on every failure path (`pr_error`, the mint message), so exit 4 or a `die` is diagnosable from the run dir alone; (3) an ambiguous outcome is reconciled, not declared failed: a non-201 or URL-less `POST /pulls` is followed by a `GET` for the open PR from this head before exit 4; (4) persist facts as they are learned (the judge's rounds and verdict go to the manifest after every round; the batch loop writes the exit status of a child that died before its cleanup), so a later failure never erases an earlier truth; (5) a verdict is exactly one `VERDICT:` line, last, in a file the bounded read did not cut, with `\r` stripped; anything else is no verdict.
