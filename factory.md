# Factory

A personal software factory on an isolated Mac mini. Autonomous coding agents (Claude Code) pick up tasks and work on my own GitHub repos. Useful first. Follows the Keycard Software Factory reference architecture and Agent Baseline controls where that is reasonable for one user on one machine.

Reviewed against a second opinion on 2026-10-28. Changes from that review are marked `(review)`.

## Non-goals for v1

Egress proxy / enforced network allowlist, Temporal, Socket, OpenShell, Kubernetes, Linear intake, agent registry tooling, multi-tenant, more than one concurrent job.

## Trust boundary (review)

The **orchestrator** on the mini is the trust boundary, not the container. It reads the task, mints credentials, builds the `docker run` command from a fixed schema, and collects results. Nothing the agent writes or says can change image, mounts, flags, repo, or token scope. Task text, repo contents, and tool output are untrusted input.

Commits are attributed to the GitHub App's bot user (`kmaida-software-factory[bot]`, email `<id>+kmaida-software-factory[bot]@users.noreply.github.com`). The orchestrator resolves the id from the public users API at the start of every run, records it in the manifest as `git_identity`, and passes it to each container as `GIT_AUTHOR_*` and `GIT_COMMITTER_*`, so the image holds no identity and the safety-net commit uses the same one. A ruleset that requires approval of unattributed changes then accepts a single human approval; the earlier made-up `factory[bot]` identity could not be attributed to any account, and keycard-workshop-platform#9 stayed `REVIEW_REQUIRED` after approval. If the lookup fails the run does not start.

## Components

### 1. Sandboxed execution

- One fresh Linux container per job (Docker Desktop or OrbStack). On macOS that is a Linux VM, so the boundary is the VM plus the container, which is stronger than Docker on a Linux host.
- Only the cloned repo is mounted, as the writable workdir. Read-only root FS. Non-root user. No Docker socket, no host home, no host network.
- Image pinned by digest. Limits: `--memory 4g --cpus 2 --pids-limit 512`, wall-clock timeout 60 min, orphan cleanup on orchestrator start. (review)
- Container is removed after the job. Artifacts are the pushed branch, the run manifest, and the run log.

### 2. No static secrets in the sandbox

- Each container gets exactly one secret, delivered over stdin as a 0400 file on a tmpfs mount, never as a `docker run` argument: the worker gets the Claude credential, the judge gets the Codex key, the push step gets the GitHub token. The worker and the judge never hold a GitHub token. (review)
  - `github_token`: a GitHub App installation token scoped to the one target repo with `contents:write` only, so the push step can push and nothing else: it cannot open, approve or merge a pull request. The orchestrator mints it for the clone and again for the push: it fetches the App's private key from Keycard Vault (resource `urn:factory:github-app-key`, a dependency of the orchestrator Application, policy-checked and audited like the Anthropic resource), signs a 10-minute app JWT in memory, looks up which installation of the App covers the repo (`GET /repos/<owner>/<name>/installation`), and calls `POST /app/installations/<id>/access_tokens` with the repo and that one permission. After the container exits, the host mints a second token with `pull_requests:write` and `contents:read` and makes the one API call that opens the PR; the container never holds it. `contents:read` is needed because `POST /repos/<owner>/<name>/pulls` resolves the head and base refs, which on a private repo returns 422 `not all refs are readable` without it; the PR token can read refs but still cannot push, approve or merge. The key is not stored on the mini. Keycard has no GitHub App connector, so repo scoping happens in the orchestrator's minting call, not in Keycard.
  - `openai_key`: the Codex judge's API key, a Keycard Vault API Token credential on the resource `https://api.openai.com`, fetched per judge round, policy-checked and audited like the App key. Keycard returns the stored key verbatim with no `expires_in` (svc-sts `SecretProvider` sets no lifetime on vault credentials), so its lifetime is the OpenAI key's own: it lasts until revoked at OpenAI or replaced in the Vault. Fetching per round gives an audit trail, not an expiry.
  - `anthropic_token`: the Claude Code credential, issued per worker round with no API key anywhere. The orchestrator authenticates to the software factory zone as its own Application (`urn:factory:mini`) and gets a one-hour Keycard-signed OIDC token for the `https://api.anthropic.com` resource, policy-checked and audited. It exchanges that at Anthropic's Workload Identity Federation endpoint for a one-hour bearer token bound to the `factory` workspace and the `factory-mini` service account. The container uses it as `ANTHROPIC_AUTH_TOKEN`.
- No PAT, no `gh auth` cache, no `.claude` auth in the image. The Anthropic and GitHub tokens live one hour, the per-container timeout.
- Known limit: a token copied out during the run stays valid until it expires or is revoked. The run log redacts both tokens (literal and the Basic-auth base64 form); that is a mitigation against accidental leaks in output, not a guarantee, since an encoded or split token survives it.
- GitHub cannot scope an installation token to a branch, so the agent's token can also push to any other branch of the target repo that no rule protects, and to other open PR branches. The ruleset protects `main`, and "dismiss stale approvals" means a push onto someone else's approved PR removes the approval rather than riding it.

### 3. Intake and task binding

- One intake for v1: a task file in `queue/` on the mini, written by me, readable but not writable by the container. (review)
- Job schema: `{repo, base_branch, task_id, instructions}`. The orchestrator validates it and derives everything else. The agent never sees or edits the job file.
- Keycard zone policy grants the run authority for that repo only.

### 4. Run manifest and log (review)

- `runs/<run_id>/manifest.json`: job hash, repo, base commit SHA, image digest, model and Claude Code version, Keycard grant id, start/end time, final commit SHA, PR URL (or `pr_error` with the HTTP status and body when opening it failed), exit status.
- `runs/<run_id>/log.jsonl`: one line per tool call and per token issue, with run id, timestamp, tool, redacted arguments, exit status. Written by the orchestrator from the agent's stream, so the agent cannot rewrite it.
- Keycard zone audit covers the authorization side.

### 5. Judge before the human gate

- No human sees the code before an independent model has tried to refute it. After each worker round the orchestrator runs Codex in its own container against a fresh clone of the worker's checkout (read-only mount of the worker's tree, agent config files stripped, instructions from `judge-prompt.md` in the factory checkout, never from the target repo). The judge reads the diff, runs the repo's checks, hunts for wrong or out-of-scope changes and weakened tests, and ends with `VERDICT: VERIFIED | CAVEATS | REFUTED` plus findings.
- Anything but VERIFIED sends the findings back to the worker as a revision round on the same branch, up to `MAX_ROUNDS` (3). A revision round that produces no new commit ends the loop.
- The branch is pushed after the loop whatever the verdict (evidence). The PR opens only on VERIFIED or CAVEATS, with the verdict and findings in the body. REFUTED exits 5 and a missing verdict exits 6, both without a PR. Each round's full review is kept as `runs/<run_id>/judge-<round>.md`.
- The judge is a model and can be wrong both ways; it narrows what reaches the human, it does not replace them.

### 5b. Verification gate (loop 0, 2026-11-02)

- Today's loop judge carries its own findings across rounds; the gate is the context-free check before anything reaches a human. After the push and the cheap gates, in the VERIFIED or CAVEATS arm: a `review` container (a fresh Claude Code session on a fresh clone at the judged head, `review-prompt.md` with the break-it lens, `--safe-mode --setting-sources "" --strict-mcp-config --disable-slash-commands --no-session-persistence`, agent config files stripped at every depth, `--json-schema` for the findings, the stream to the run log and the last result event's structured output to `/out/review.json` by a `node -e` line) then a `verify` container (`verify.js` mounted from this checkout, no model, no credential, egress to the npm registry only: clones `/src`, `npm ci` once per checkout when there is a `package.json`, runs each BLOCK's repro with `bash -o pipefail -c` under a 300 s timeout at the head and at the base, with `checkout -f` and `clean -fdx -e node_modules` between, and the two differential test checks: the base's changed test files against the head's code, the head's against the base's). Findings are JSON (`{"blocks":[{"loc","claim","clause","repro"}],"notes":[…]}`), at most `MAX_BLOCKS` (10) blocks per review.
- Execution is the verdict: the host classifies each BLOCK from the two exit codes. Invalid (head exit 0, 124, 126, 127 or ≥128), regression (head fails, base passes), unmet (both fail, a Done when clause named), pre-existing (both fail, no clause: a note). Only regression and unmet count. The differential checks are notes for the PR body in PR-only mode.
- Cycles: nothing reproduced opens the PR with the gate's record in the body. Otherwise the reproduced findings go to one worker round as orchestrator facts ("a verification gate reproduced these; the loop judge had passed the branch"), one judge round with the same facts in its facts section, the push, and the gate again; `judge.rounds` counts the cycle's round, and cycles run past `MAX_ROUNDS`. Dead, on no progress: no new commits in a cycle, a repro that reproduced in an earlier cycle, REFUTED from the loop judge in a cycle, or `MAX_GATES` (4) cycles: `outcome: refuted`, `refuted_by: gate`, exit 5, no PR.
- Missing verification is not approval: a review or verifier that crashed, left no file, an invalid file, or a failed install is `outcome: gate_pending`, exit 12, class infra (the batch retries the task once as `-i1`; re-gating the pushed head in place without a new worker run is loop 7's replay, not yet built). A stop (`HALT`) landing after the push is `gate_pending` too, with `halted: true` in the cycle.
- The manifest records `gate: {cycles: [{reviews: [{lens, arm, model, status, valid, blocks, notes, truncated}], verifier: {status, valid, install, checks, blocks: [{loc, claim, clause, repro, head_exit, base_exit, class}]}, reproduced}], result}` after every cycle; the evidence files are `gate-<cycle>-breakit.json` and `gate-<cycle>-verify.json`. Blocked, dependency-change and conflict branches never reach the gate.
- Not in this step: the Codex integrity lens (scope, weakened tests, mocked-away behaviour as NOTEs; its mechanically checkable parts are the differential checks here and the host gates) and the merge into `next` (the gate opens PRs; option (b) of the plan until the canary and the negative ruleset tests pass).

### 6. Human gate on merge

- The host opens the PR after a passing verdict. CI runs. I merge.
- Enforced in GitHub, not by instruction: a ruleset on `main` (PR required, one approval, stale approvals dismissed, required check), the agent's token cannot review or merge, and the App is not in the bypass list. (review)
- Target-repo requirement: workflows that run on `pull_request` must not use repository secrets. A `factory/*` branch is a same-repo branch, so GitHub gives its workflow runs the repo's secrets, and the agent can change any script those workflows execute. The App has no `workflows` permission, so it cannot edit the workflow files themselves. `plan-my-today`'s CI uses dummy values and no secrets.

### 6b. The merge gate: `next`, merged by the factory through its PR (loop 7 step, 2026-11-02; option (c) of docs/cascade-plan.md)

- A task whose `base_branch` is `next` and a non-empty `MERGER_APP_ID` put a run in merge mode: after the verification gate passed and the PR is open, `merge_next` merges the PR into `next` with a separate merger App's token, minted for that step and held by no container. Only when the chain base (`base_sha`) is already an ancestor of `next`'s tip (chain taint: a task chained above one held for a human would land that ancestor unseen) and the accumulation cap is not reached (`MERGE_CAP_COMMITS` commits, about two per merge, or `MERGE_CAP_LINES` changed lines in `next...main`: past either the factory opens PRs instead so the promotion review stays readable). It posts the `factory-gate` check run on the gated head with the verifier record's sha256, waits (bounded by `MERGE_WAIT_SEC`) for the PR to be mergeable, merges by `sha` (409 if the head moved), and reconciles a lost or refused answer by reading the PR before calling it open (`unknown` when the PR cannot be read back, or when an unanswered merge may still land; `factory status` settles those). A stop (`HALT`) before the merge leaves the PR open. The manifest records `merge: {state: merged|held|open|timeout|unknown, sha, reason}`; the exit status is the PR's (0): a PR that did not merge is still a PR, for `factory status`. `MERGER_APP_ID` empty is PR-only mode, the mode until the ruleset and the App exist and the two checks below pass.
- The batch in merge mode first checks that `main` is contained in `next` (compare `next...main` is `behind` or `identical`) for every GitHub repo the queue's `next`-based tasks target, and stops with a notification otherwise: a hotfix on `main` not forward-merged would be built on a `next` that lacks it and lost at the promotion.
- **Setup, once, by the operator** (the parity thread's ruleset work): create `next` from `main`; a ruleset on `next`: pull request required, 0 approvals, required checks `test` (pinned to Actions) and `factory-gate` (pinned to the merger App), merge commits only, no force push, no App on the bypass list; `next` is not pushable by the push token (the parity ruleset that restricts updates to `factory/**` covers it); "require branches up to date" off. A second GitHub App, the merger (checks:write, contents:write, pull_requests:write: the merge endpoint needs the last two, the check run the first), installed on the target repo, its private key a Keycard Vault credential on the resource `urn:factory:merger-app-key` permitted to `urn:factory:mini`, so its use is audited and revocable from a phone without stopping the push App. Then `MERGER_APP_ID` (the App's client id) by PR.
- **`factory ruleset-check <owner/name>`**, the negative tests with real tokens, run by hand on the mini after the setup: the push token cannot push to `next` (and `next` did not move); a merge without `factory-gate` is refused; the rules on `next` name `factory-gate`; the merger App can post `factory-gate`; a merge with a stale sha is 409; with the check and the required checks green the merge lands (an empty commit on `next`, which proves the positive path); an App merge on `main` is refused (an App approval is reported as a note: whether it counts is what the merge shows). A transport error or a 5xx is inconclusive, never a PASS. It leaves `factory/ruleset-check-<ts>` on the repo (deletions are restricted) and closes its two PRs. Record the ruleset ids and the output here when it passes.
- **`canary.sh <owner/name>`**, the factory's own canary queue against a throwaway repo, run on the mini after every factory merge and before a real night: a task that passes the gate (and merges in merge mode), an impossible Scope (blocked, no judge round), a dependent of it (waits on a dead task), a dependency-manifest change (refused). Asserts each manifest. The weakened-test and forced-BLOCK canaries need a fixture repo with a test suite; the injected infra fault needs loop 7's replay; neither is here yet.
- Kill switch from a phone: set `next`'s ruleset to require one approval, or suspend the merger App. The promotion `next` → `main` and the revert procedure are `factory status` (loop 6).

### 7. Kill switch

- One script, `factory stop <run_id>`: stops the run's container, blocks new dispatch, and records the incident (in the log always; in the manifest when no live orchestrator will finalize it). Revocation is not wired: the orchestrator keeps no token to revoke, and both expire within the hour. (review)
- Known limit: revocation does not undo work already pushed. The PR gate catches that.

## Flow

```
task file in queue/
  -> orchestrator validates job, creates run_id, writes manifest
  -> orchestrator mints repo-scoped GitHub token from the App, fetches Claude credential from Keycard
  -> each container gets its one secret over stdin, landing as a 0400 file on tmpfs
  -> docker run (pinned image, repo mount, secrets mount, limits)
  -> worker container: agent works and commits; orchestrator streams tool calls to log.jsonl
  -> judge container: Codex reviews a fresh clone, writes findings + VERDICT
  -> not VERIFIED and rounds left: worker container again with the findings; else continue
  -> push container pushes the branch
  -> verification gate (VERIFIED or CAVEATS, cheap gates clean): review container (fresh Claude, break-it lens, JSON BLOCKs with repro commands)
     -> verify container (no model, no credential: each repro at head and at base, the differential test checks)
     -> a reproduced BLOCK: one worker round and one judge round with the facts, push, gate again; else the host opens the PR
  -> containers removed, manifest finalized (judge rounds and verdict recorded)
  -> human reviews and merges
```

## Accepted risks for v1

- Open egress from the containers. The worker can exfiltrate the repo and its Anthropic token over HTTPS. In the judge container, the repo's own checks run as the same user as Codex with no inner sandbox, so a test the worker wrote can read Codex's login under `/tmp/codex` and send the judge's key out (v1's CI judge had the same exposure). The git helper only answers for github.com, so a push to another host carries no credential, but `curl` would. Mitigations in place: the judge's key is judge-only and rotatable, the verdict is collected from a mount the repo cannot reach, and anything the judge writes is redacted for its key before it is reused. Revisit with the Keycard egress proxy, or a credential-free check container feeding the judge, when this matters.
- Single machine, single user, no evidence integrity.

## Files

- `factory.md`: this spec.
- `Dockerfile`: the sandbox image; one entrypoint with three modes (`work`, `judge`, `push`), one container per step.
- `worker-prompt.md`: the house rules prepended to every worker round (least code that satisfies "Done when"; no speculative abstraction; one test per behaviour; no new dependencies), read from this checkout.
- `judge-prompt.md`: the judge's instructions, read from this checkout, never from the target repo. Over-engineering is a finding with the weight of a bug and earns CAVEATS, so bloat costs the worker a revision round. Every round reports every finding the judge can establish, ranked, each marked `NEW:` or `REPEAT:` against the previous round's findings, which the orchestrator appends to the judge's prompt from round 2 on as another session's claims, beside its own facts (loop 4: REPEAT only when re-established at the new head) (run `011-wp-join-core`, 2026-10-31, was refuted in round 3 by a finding first raised in round 3, with no round left to fix it). A finding that a change is unnecessary must be tested before it is written, a REPEAT must be re-tested when the agent answered it with command output, and a check that passes only with an out-of-scope change is reported as "blocked" in the round it is found (run `050b-wp-web-auth`, 2026-11-01, was told for three rounds that imports already listed `apps/web/auth.ts` in its composite project; the judge first tried it in round 4, saw TS6307, and the agent had reverted a working implementation by then).
- `README.md` ("Writing tasks"): task-writing conventions for unattended runs; `factory lint` checks a queue against them and `batch` refuses to start on problems.
- `factory`: orchestrator script (`run`, `lint`, `batch`, `report`, `stop`). `batch` is the overnight loop (section below). `run` exits with the worker's status, or 3 when the agent produced no commits (nothing pushed), 4 when the branch was pushed but opening the PR failed, 5 when the judge refuted the final round (pushed, no PR), 6 when the judge gave no verdict (pushed, no PR).
- `test-factory.sh`: runs the orchestrator against stubbed `docker` and `curl` and checks the revise / refuted / no-verdict / caveats paths, CRLF, doubled and oversize verdict files, the judged-round count, log redaction, lint and batch (chain, refuted chain, `--max-tasks`, `--stop-at`, HALT between tasks, `--no-chain`, `--continue`, a declared dependency on a failed task, a run killed before its cleanup, task files byte-identical after the move), the GitHub App path (installation lookup, 404, refused mint, PR open, PR reconciliation, chained PRs targeting `base_branch`) and `stop` with docker down. Every fix for a misreported outcome lands with a case here that fails against the previous script.
- `review-prompt.md`: the verification gate's reviewer, the break-it lens, JSON findings with a repro command per BLOCK; read from this checkout.
- `verify.js`: the verifier, mounted read-only into the `verify` container like `proxy.js`; runs the repro commands and the differential test checks, records exit codes only.
- `queue/`, `runs/`: task intake and per-run evidence. Not in the image.

## Batch and overnight runs

`factory batch [queue-dir] [--max-tasks N] [--stop-at HH:MM] [--no-chain] [--continue]` runs a queue (default `queue/`) unattended without waiting for anything to merge. A run on its own bases on `base_branch` and stops; a second task that builds on the first has nothing to build on until a human merges, so an overnight queue would stall after one task. `batch` chains instead.

- **Chaining.** Tasks run in task-id order under one lock (each run borrows it and hands it back): the queue is listed afresh before every run and the smallest id after the last one taken runs next, so a file the loop writes itself (an infra retry, `<id>-i1`) runs next; ids, not filenames, because `<id>-i1.json` sorts before `<id>.json` (`-` before `.`) while the id `<id>-i1` sorts after `<id>`, and `LC_ALL=C` so the order is the same on every host. The first task bases on its own `base_branch`. Every task after a task that exited 0 cuts its branch from `factory/<previous task_id>`: `batch` passes it to `run` as `FACTORY_CHAIN_BASE`; the task file is never changed. The PR still targets the task's own `base_branch` (a PR opened against `factory/<prev>` fails with 422 "base ref not found" once that branch is merged and auto-deleted mid-batch), so a stacked PR shows the earlier task's commits until it merges. The manifest records `base_branch` (the PR base) and `chain_base` (the branch it was cut from, null when not chained). `--no-chain` makes every task base on its own `base_branch`.
- **Task or infra (2026-11-02, after the 2026-11-01 batch).** Every failed run carries `class` in its manifest, decided by `CLASS_JQ` from the outcome and the round state, never from the number alone (a worker container's own exit code passes through as the run's status). Task: `refuted`, `blocked`, `dependency_change`, `credential_in_input`, `branch_exists`, or a worker that exited 3 (no changes); the task cannot pass as specified. A `factory stop` writes `outcome: stopped` before it signals, so a stopped task is the operator's decision (class task, `failed/`), never something the batch re-dispatches once `HALT` is removed. Infra: everything else: no verdict (6), `conflict` (11, the target moved), `gate_error` and `evidence_error` (12), `push_failed`, `pr_failed` (4), a worker round that failed, a token or proxy `die` (1), a kill (137). `END_JQ` applies the rule to every manifest at its end, however the run ended (finalisation, `cleanup` after a `die`, `stop`, the batch after a kill), and settles `pushed`: true, false, or null when the push step started and its result is unknown (`push_attempted` is written before the push container runs; a `die` collecting its record, or `evidence_error` on that step, leaves it null), which the batch treats as pushed because the branch may be on GitHub and the id would then be refused. `final_sha` is set only when the push succeeded (a failed push used to record the judged sha as if pushed; it is now `push_failed`, `final_sha` null). An infra failure never stops the batch on its own: nothing pushed, the file stays in the queue under its own id (the id is reusable, nothing is on GitHub); pushed, the task is archived to `failed/` and retried once, next, as `<id>-i1` from the same chain base. The retry is taken by name before the listing and leaves the cursor where it was, so an id that sorts between `<id>` and `<id>-i1` is neither skipped nor run first. A conflict is the exception: with no chain head it retries from the task's own base (the branch it conflicted with); mid-chain it is not retried (from the base the retry would drop the chain's unmerged work, from the chain it would conflict again) and is archived with that reason. The retry file is written after the original is archived, so a kill between the two leaves nothing to run twice. A retry that ends with the same exit and outcome as its original is a task failure: the retry proved it reproducible; the manifest records `class_note`. Every non-pass, retry or not, puts the task's id and base id in the `failed` list, so a task declaring `base_branch: factory/<id>` is skipped under `--continue` rather than built on the evidence branch. Two infra failures in a row from different tasks stop the batch with the queue as it is (the circuit breaker: one operator, one mini, a third attempt at 3 a.m. is a third identical failure); a pass or a task failure resets the streak and its history. `pr_failed` (judged, pushed, every gate clean, only the PR missing) is a pass for the chain, decided from the outcome and never from the number 4 (a worker's own exit code passes through as the run's status): `done/`, the chain goes on from it, the batch exits 0 for it, and the notification says to open the PR by hand. The batch's exit status is each task's standing by its last run tonight (base ids: a retry that passed clears its original, a later failure under the same base id counts), the latest task whose last run did not pass, 0 when every task's last run passed. Ids ending in `-i<N>` are the batch's; do not write them by hand. A task file added after lint ran at the start is checked against the schema when it is picked: a malformed one gets a row and `failed/`, never a dead batch. Report rows gain a NOTE column (`retrying as …`, `nothing pushed; left in queue`, `retry failed the same way`, `PR open failed; …`), the summary counts `infra` apart from `failed`.
- **Declared dependencies (2026-11-02, after the 2026-11-01 batch, where two failed roots took 15 dependents down one by one).** An optional `depends_on` list of task ids in the task file (`JOB_SCHEMA` allows exactly that fifth key). Ids are compared as base ids (`base_id` strips every `-r<N>` and `-i<N>`), so a requeue or a retry of a task counts for it. `lint` prints `graph: <id> <- <deps>` and refuses a dependency on the task itself, an unknown id (not in the queue, `done/` or `failed/`), a task of another repo, or a later task in the queue: filename order is the schedule, so the author reorders rather than the batch waiting a night. Before a task runs, `cmd_batch` asks `dep_state` for each dependency: `merged` (GitHub: a merged PR from `factory/<id>` or one of its `-r<N>`/`-i<N>` heads, and no merged PR titled `Revert "factory: <id>"`, the revert button's title; for a local repo, the run's `final_sha` is an ancestor of the base branch), `open` (a PR exists), `queued` (a run of it is still in the queue: a retry, a requeue, an infra failure left for tomorrow), `unknown` (GitHub answered anything but 200 with an array or a search result, no token could be minted, the run record is pruned, or the base cannot be fetched: a wait, notified, never a verdict either way, since a lookup failure that read as "dead" would notify a false death and one that read as "merged" would run a dependant on a base without its root), `reverted`, or `dead` (failed with nothing queued, closed unmerged, or merged into another branch than the dependant's base: the PR's `base.ref` is checked, since a stacked task's PR merges into `factory/<prev>`). Every candidate is examined and the states settle by precedence (merged, queued, open, unknown, reverted, dead), never by archive order; a revert is a merged PR whose title is exactly `Revert "factory: <id>"` (the search narrows, the title decides, so a reverted `-r1` is not the original's revert). Every dependency of a task is asked and the worst answer decides (dead over unknown over a live wait), so a live first dependency never hides a dead second. The read-only token is minted once per batch per repo and cached in the lock dir (`dep_tok`, owner-only; refreshed after 50 min). `done/` is never the truth for merged: it only says a PR was opened, and a task that trusted it would run on a base without its predecessor. In chain mode a dependency that passed tonight is satisfied (the linear chain holds every passed task); under `--no-chain` only merged counts. The GitHub questions use a read-only token (pull_requests:read, contents:read) minted once per repo, only when a check needs it (`gh_read_token`, with `rundir` unset so no run's manifest gets that installation id); a local repo uses the file token. Anything but merged makes the task wait: a row (`waiting on <id> (<state>)`), the file untouched, visited once per night by the cursor, released the night after the dependency lands; `dead` is said in the row, notified, and counted as a failed task for the exit status (`outcomes` gets `<id>=1`), so a night where everything waits on one dead root is never a quiet exit 0. Not done: a wait older than one night is not told apart from a fresh one (the row and the notification repeat each night).
- **Stopping.** A task-class exit ends the batch unless `--continue`: that task's file moves to `<queue-dir>/failed/`, every later task stays in the queue untouched. `--continue` goes on instead: the failed task goes to `failed/`, every later task whose base (its own `base_branch`, or the chain) names a task that failed tonight is moved to `failed/` unrun, since that branch was pushed as evidence and must not be built on, and the chain resumes from the next task's own `base_branch`. `--max-tasks N` and `--stop-at HH:MM` (today at that local time: no task starts once it has passed, so a time already past means nothing runs; a batch meant to cross midnight should start after it) stop the batch between tasks in the same way, moving nothing further. A chained queue targets one repo; `batch` refuses a mixed one unless `--no-chain`.
- **Task files.** Exit 0 or 4 moves the file to `<queue-dir>/done/<run_id>.json`, a task-class or pushed-infra failure to `<queue-dir>/failed/<run_id>.json`, an infra failure with nothing pushed leaves it where it is (`run_id` is `<timestamp>-<task_id>`, and lint makes `task_id` the filename; a task that died before it became a run gets `batch-<timestamp>-<name>.json`). A rerun of `batch` therefore never repeats a task. The bytes do not change, only the path. This is what happens to a task file after its run; a bare `factory run` still leaves the file where it is.
- **Report.** `runs/batch-<timestamp>.md`: one row per task with the `report` columns (run, exit, judge rounds, verdict, PR) plus the chain base and the duration, and the reason the batch stopped if it did. The path is printed last. The header names the notify host (or `off`). `batch` exits with the status of the last run whose task did not pass tonight, 0 otherwise.
- **Notify.** With `FACTORY_NOTIFY_URL` set (an env var like `FACTORY_SECRETS_DIR`, never a constant in `factory`), every task that exits non-zero POSTs one line to it with curl: `<batch_id>: <task name> exited <rc> (<outcome or verdict, "infra: " prefixed for that class>, <continuing|stopped|retrying as <id>-i1|left in queue>)`. 10 s timeout; a failed POST is not retried, but it is printed to stderr as `notify: POST failed (curl exit N)` (the 2026-11-01 batch ran with the variable unset, from a shell that had not read `.zshrc`, and nothing said so: `batch` now prints `notify: <host>` or `notify: off (FACTORY_NOTIFY_URL not set)` after taking the lock and in the report header, the host only, cut before the path that carries the topic; the export belongs in `~/.zshenv`, which ssh one-liners and launchd read). The URL goes to curl as config on stdin, not argv, since webhook URLs often carry a token. `batch` refuses to start on a URL with quotes, backslashes or whitespace, which could break that config. Nothing is sent for a passing task or a task skipped unrun (GitHub already notifies on every PR the App opens). When the loop is over, one summary line follows whatever happened: `<batch_id>: done: <n> run, <k> PR(s), <f> failed[, <b> blocked][, <i> infra]. <All tasks ran.|Stopped: <why>. <m> task(s) left in queue.>`, so a night with no message at all means the batch never reached its end (refused at start by lint, `HALT` or the lock, or killed), the variable was not in its environment (`notify: off` in its output), or the endpoint was unreachable (`notify: POST failed` on its stderr); `runs/batch-<timestamp>.md` settles which. The body is raw text, so an ntfy topic (`https://ntfy.sh/<topic>`, the topic being the secret) works as is; a Slack webhook would need a JSON body.
- **Stop.** `factory stop <run_id>` writes `HALT` and signals the run; the run exits non-zero and goes to `failed/`, and the batch loop sees `HALT` before the next task and exits, moving nothing else. `batch` also refuses to start while `HALT` exists.
- **Why `main` is never merged by the mini.** Chaining needs no merge: each branch is pushed by the push container with a `contents:write` token and the PR is opened by the host with `pull_requests:write`. Nothing on the mini holds approval or merge rights, the App is not in the ruleset's bypass list, and the trust boundary, container flags, secrets delivery and judge are exactly those of a single `run`.
- **Morning routine.** `factory report`, then the stack bottom-up: every PR targets its task's `base_branch` (normally `main`), so a later PR's diff includes the tasks below it until they merge. Review and merge the bottom PR; the next one's diff shrinks to its own commits. A task in `failed/` has its reason in `runs/<run_id>/manifest.json` and `judge-<round>.md`; to re-queue it, copy the file back into the queue under a new `task_id` (the old `factory/<task_id>` branch exists, so a rerun with the same id is refused), append the judge's findings to its instructions, and run `batch` again. Everything that was queued after it is still there and will chain on the re-queued task.
- **Blocked tasks (loop 4, 2026-11-02).** The worker prompt says: when the task cannot be done against the branch as it is, or a reviewer finding can only be satisfied by leaving Scope, adding a forbidden dependency or a prerequisite not on the branch, commit `docs/BLOCKED-<task_id>.md` with the reason and stop. The note ends the run before the judge: after each worker round the orchestrator checks for the note at the round's head and, if it is there, skips the judge and goes to the push, so a round-1 note is `judge:{rounds:0, verdict:null}` and a later one keeps the earlier rounds' record (last night's 18 blocked tasks each spent a judge round and an empty revision round on a note). The gate then decides `blocked` from the pushed head (`git ls-tree` in the bare gate repo: a regular file at that path, with `--no-replace-objects`; a git failure is `gate_error`), not from "the only change is a note": a note on top of code is blocked, a note committed and deleted again is not, and another task's note on the chain base is not. Gate order: fetch and diff, the dependency-manifest gate (a note beside a manifest change is still a manifest change), blocked, then the verdict switch, where a VERIFIED or CAVEATS verdict applies only to the head it judged: a pushed head the judge never saw (the worker's checkout can lie to the loop's note check through `refs/replace`) is `gate_error`, never a PR. The worker's prompt names its `task_id` and the note path, and `requeue` and the `-i1` retry rewrite `docs/BLOCKED-<old id>.md` in the task text to the new id, so a rerun does not write the original's name and get refuted instead of blocked. Exit 10, branch pushed, no PR, the note's first body line as `reason`. The judge's prompt from round 2 on separates what the orchestrator saw (the commit the previous round judged, this round's head) from the previous round's findings, which arrive as another reviewer session's claims: REPEAT only when re-established at the new head (the 050b judge carried an untested claim for three rounds).
